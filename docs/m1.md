# M1 — первый рабочий рубеж

Цель: «официальный образ → проверяемая запись → сохранённый результат → установка → реальный вход в WinRE».

## Фикстура

Решение владельца от 27.10.2026: базовая фикстура M1 — **официальный Windows 11 26H2 Pro x64** (сборка 10.0.26300), одноиндексная WIM, подготовленная по шагу 1 пакета M1-EXP-A. Это вместо 25H2 из плана по умолчанию; 25H2 проверяется на этапе матрицы. SHA-256 фикстуры (`C:\IF\fixture\media\sources\install.wim`): `F240257D104BC1271A8DD6CF5244B51313DAC5FD1F5B6D724B8C3690C7C10A09`.

Решение владельца от 28.10.2026: проверки установки и WinRE (M1 4–6) выполняются в **VirtualBox 7** (EFI, Secure Boot, TPM 2.0) вместо Hyper-V из плана. Hyper-V остаётся в матрице следующих этапов.

## Журнал работ

### RPC-транспорт с ограничением размера

- `ImageForge.Core.Rpc.EngineRpc` — единая точка создания JSON-RPC соединения для App и Engine.Host.
- Кадр: 4 байта длины (big-endian) + JSON (System.Text.Json). Длина больше лимита отклоняется до чтения тела, соединение разрывается.
- Лимиты: движок принимает до 1 MiB и отправляет до 16 MiB; клиент — наоборот.
- Ранний транспортный тест (`RpcTransportTests`, выполняется в CI): типизированный вызов, `IProgress<T>` в порядке отправки, отмена `CancellationToken` доходит до сервера, превышение лимита на приёме и на отправке, обрезанный кадр.

### Эксперименты 1 и 3: DISM и офлайн-куст

- Core (TDD): `RegistryPlanExecutor` — load → set → unload; при любой ошибке или отмене загруженные кусты выгружаются, невыгруженный куст переводит в RecoveryRequired. `HiveLoadName` — уникальные имена загрузки с признаком владения. `OfflineHivePaths` — путь куста только внутри mount. `DismCliArguments` — export отдельными аргументами.
- Engine: `Win32OfflineHiveLoader` (RegLoadKey/RegUnLoadKey с SeBackup/SeRestore только на время вызова, запись посегментно с `REG_OPTION_OPEN_LINK`, отказ от символьных ссылок, ограниченные ретраи выгрузки), `DismImages` (ManagedDism), `DismCli` (Dism.exe из System32, без оболочки).
- `tools/ImageForge.Experiments` — self-contained утилита для ручных экспериментов в VM; CI публикует её с SHA-256.

### Эксперимент 2: UAC и канал

- Первая сборка падала при старте в VM: без `EnableMsixTooling` не генерировался `ImageForge.App.pri`. Исправлено; CI теперь запускает опубликованное приложение и падает, если окно не держится 20 секунд. Необработанные исключения UI пишутся в `%LOCALAPPDATA%\ImageForge\logs\app-crash.log`.
- App и Engine.Host публикуются self-contained (win-x64); CI собирает артефакт `ImageForge.App-<sha>` с движком в `engine\` и SHA-256 обоих exe.

### Рабочая папка и публикация результата

- Core (TDD), пространство имён `ImageForge.Core.Workspace`:
  - `WorkspaceLocations` — источник, рабочая папка и папка результата должны быть локальными путями и не совпадать и не вкладываться друг в друга ни в какую сторону.
  - `WorkspaceLayout` — фиксированные пути `base\`, `runs\<RunId>\working|completed|assemble`, `mount\<ImageId>`, `scratch`, `logs`, `state.json`, `journal\<RunId>.jsonl`; каждый путь проходит через `WriteScope` рабочей папки.
  - `SourceManifest` — размер и SHA-256 каждого файла источника и общий отпечаток; сравнение показывает добавленные, удалённые и изменённые файлы. Используется, чтобы доказать неизменность источника и копии в `base\`.
  - `RunJournal` — журнал запуска в JSON Lines; каждая запись сбрасывается на диск. Обрезанная строка, разрыв в номерах или чужой RunId означают повреждение: дописывать в такой журнал нельзя, запуск идёт в восстановление. `LastOpenStep` показывает шаг, который начался и не закончился.
  - `StateStore<T>` — `state.json` пишется во временный файл и атомарно заменяется (`File.Replace`) с сохранением предыдущей версии в `.bak`; при повреждённом текущем файле читается предыдущая, при повреждении обеих — состояние Unusable.
  - `ResultPublisher` — результат собирается в скрытой соседней папке `.<имя>.imageforge-<RunId>.staging`; старый результат переименовывается в `.previous`, staging — в папку результата, затем старый удаляется. `PublicationRecovery` после сбоя: возвращает старый результат, если нового нет; удаляет незаконченный staging; staging никогда не считается готовым результатом.

### Эксперимент 4: полный запуск и сбой до публикации

- Core (TDD): `RunPipeline` — копия источника в `base\` с проверкой отпечатка (повторно используется, если источник не менялся), рабочая копия `install.wim`, mount, план реестра, commit, export, сборка результата в staging рядом с папкой вывода с проверкой по манифесту, повторная сверка источника, публикация. Любой сбой: образ отмонтируется без сохранения, staging удаляется или возвращается предыдущий результат, папка запуска удаляется, цель получает `NeedsRebuild`; если что-то освободить не удалось — `RecoveryRequired`, и новый запуск не стартует.
- `RunRecovery` после аварийного завершения: выгружает кусты запуска, отмонтирует только его образ без сохранения, завершает публикацию через `PublicationRecovery`, удаляет папку запуска. Чужие монтирования не трогаются.
- Engine: `DismImageServicing` (DISM API, `Dism.exe /Export-Image`, офлайн-кусты), `Win32OfflineHiveLoader.UnloadOwned`.
- Утилита: команды `run` (с точками сбоя `after-mount`, `before-publish` и паузами для аварийного завершения), `status`, `recover`, `manifest`.

### Запуск из окна приложения

- Core (TDD): `WorkspaceSession` — открыть рабочую папку (с проверкой расположения папок), построить план M1, запустить только показанный план (PlanId, ревизия, отпечаток; повтор с тем же ClientRequestId не запускает второй раз), восстановить. Ревизия меняется при каждом открытии, запуске и восстановлении.
- RPC-контракт v2: `OpenWorkspaceAsync`, `GetWorkspaceAsync`, `PlanAsync`, `StartAsync` (поток строк прогресса), `RecoverAsync`; тест прогоняет контракт через ограниченный транспорт.
- Engine: одна сессия DISM на всё время жизни; строки прогресса дублируются в лог движка.
- App: три папки, «Подготовить» (превью от движка), «Запустить», «Восстановить», журнал, ссылка на результат; изменение папок сбрасывает план.
