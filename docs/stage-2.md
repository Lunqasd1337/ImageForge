# Этап 2 — основные операции

Порядок по плану: `.reg`, Appx, Features/Capabilities, драйверы, обновления Windows; каждая возможность с тестами и проверкой в VM.

Решение владельца от 28.10.2026: поддерживается только формат **Windows Registry Editor Version 5.00**. Файлы REGEDIT4 отклоняются с понятной ошибкой (план, раздел 9, называл оба формата).

## Журнал работ

### Импорт .reg: загрузчик и парсер

- Core (TDD), `ImageForge.Core.Registry.RegFile`:
  - `RegFileLoader` — байты в текст. BOM решает UTF-16LE или UTF-8. Без BOM чистый ASCII читается сразу; текст с нулевыми байтами или корректный UTF-8 с не-ASCII блокируется как неоднозначный, пока пользователь не выберет кодировку; иначе — ANSI с показанной кодовой страницей (для файлов 5.00, сохранённых в блокноте не в Юникоде). Некорректные байты, UTF-16BE и неизвестная кодовая страница блокируют импорт.
  - `RegFileParser` — Version 5.00 (REGEDIT4 распознаётся и отклоняется, `regfile.format.unsupported`): `[key]`, `[-key]`, именованные и `@` значения, `=-`, строки с экранированием `\\` и `\"`, `dword:`, `hex:` и `hex(0..b):` с продолжением строк, комментарии `;` (внутри строки `;` — данные). Порядок операций сохраняется, включая повторы и удаления. Каждая ошибка — с номером строки, любая ошибка блокирует весь файл. Типы вне 0..b блокируются.
  - `RegData` хранит тип и байты ровно в том виде, в каком их записывает `RegSetValueEx`: строки — UTF-16LE с завершающим нулём, `REG_EXPAND_SZ` без раскрытия переменных.
- Утилита: `reg-check <file.reg> <encoding> <code-page> <key>` — разбор файла и побайтное сравнение каждого значения с живым реестром (только чтение). Проверка в VM — [S2-REG-PARSE](vm-checks/S2-REG-PARSE.md).
- Маппинг всех корней из таблицы плана (`RegistryPathMapper`): SOFTWARE, SYSTEM (CurrentControlSet только через `Select\Current` образа), NTUSER.DAT и UsrClass.dat профиля Default, DEFAULT, HKCR в машинные классы по политике. Остальное блокируется.

### Применение .reg к офлайн-кустам

- Core (TDD): `RegistryValue` — тип и байты ровно для `RegSetValueEx` (общий для парсера, плана и движка). Изменения `SetRegistryValue`, `DeleteRegistryValue`, `CreateRegistryKey`, `DeleteRegistryKey`; `RegFileChanges.From` переводит разобранный файл в изменения в порядке файла.
- План: один load/unload на куст, порядок внутри куста сохраняется; шаги несут признак CurrentControlSet. Удаление корня куста блокируется. Отпечаток плана (формат 2) включает байты значений.
- Исполнитель: CurrentControlSet разрешается один раз на куст из `Select\Current`; без него шаг падает, ControlSet001 не подставляется. До первой записи проверяется, что все файлы кустов плана есть в образе: в `install.wim` нет `UsrClass.dat` профиля Default, поэтому изменения `HKCU\Software\Classes` в этот куст не пишутся (найдено в VM).
- `HKCU\Software\Classes` — через первый вход (решение владельца): изменения собираются в .reg (v5, UTF-16, `RegFileWriter`), файл кладётся в `ProgramData\ImageForge\FirstLogon` образа (`MountFileWriter`, без перехода по ссылкам и junction), а в SOFTWARE регистрируется компонент Active Setup с `StubPath` `reg.exe import`. Имя файла и GUID компонента — от хеша содержимого. Ни в какой другой куст эти изменения не пишутся. Проверка: шаг 2б [S2-REG-APPLY](vm-checks/S2-REG-APPLY.md) и [S2-FIRST-LOGON](vm-checks/S2-FIRST-LOGON.md).
- Найдено в VM: удаление значения открывало ключ только на чтение («Отказано в доступе»), исправлено.
- Engine: запись сырых байтов любого типа 0..b, удаление значения, создание ключа, удаление дерева в глубину без перехода по символьным ссылкам (дерево со ссылкой не удаляется).
- Превью: общий русский текст для окна и утилиты (`RegistryPreviewText`).
- Утилита: `reg-apply` и `reg-verify` — применить файл к смонтированному образу и проверить итог. Проверка в VM — [S2-REG-APPLY](vm-checks/S2-REG-APPLY.md).
- Дальше: прежние данные в превью, импорт файла из окна (экран «Реестр»), запуск с изменениями из файла.
