# Этап 2 — основные операции

Порядок по плану: `.reg`, Appx, Features/Capabilities, драйверы, обновления Windows; каждая возможность с тестами и проверкой в VM.

Решение владельца от 28.10.2026: поддерживается только формат **Windows Registry Editor Version 5.00**. Файлы REGEDIT4 отклоняются с понятной ошибкой (план, раздел 9, называл оба формата).

## Журнал работ

### Импорт .reg: загрузчик и парсер

- Core (TDD), `ImageForge.Core.Registry.RegFile`:
  - `RegFileLoader` — байты в текст. BOM решает UTF-16LE или UTF-8. Без BOM чистый ASCII читается сразу; текст с нулевыми байтами или корректный UTF-8 с не-ASCII блокируется как неоднозначный, пока пользователь не выберет кодировку; иначе — ANSI с показанной кодовой страницей (для файлов 5.00, сохранённых в блокноте не в Юникоде). Некорректные байты, UTF-16BE и неизвестная кодовая страница блокируют импорт.
  - `RegFileParser` — Version 5.00 (REGEDIT4 распознаётся и отклоняется, `regfile.format.unsupported`): `[key]`, `[-key]`, именованные и `@` значения, `=-`, строки с экранированием `\\` и `\"`, `dword:`, `hex:` и `hex(0..b):` с продолжением строк, комментарии `;` (внутри строки `;` — данные). Порядок операций сохраняется, включая повторы и удаления. Каждая ошибка — с номером строки, любая ошибка блокирует весь файл. Типы вне 0..b блокируются.
  - `RegData` хранит тип и байты ровно в том виде, в каком их записывает `RegSetValueEx`: строки — UTF-16LE с завершающим нулём, `REG_EXPAND_SZ` без раскрытия переменных.
- Утилита: `reg-check <file.reg> <encoding> <code-page> <key>` — разбор файла и побайтное сравнение каждого значения с живым реестром (только чтение). Проверка в VM — [S2-REG-PARSE](vm-checks/S2-REG-PARSE.md).
- Маппинг всех корней из таблицы плана (`RegistryPathMapper`): SOFTWARE, SYSTEM (CurrentControlSet только через `Select\Current` образа), NTUSER.DAT и UsrClass.dat профиля Default, DEFAULT, HKCR в машинные классы по политике. Остальное блокируется.

### Применение .reg к офлайн-кустам

- Core (TDD): `RegistryValue` — тип и байты ровно для `RegSetValueEx` (общий для парсера, плана и движка). Изменения `SetRegistryValue`, `DeleteRegistryValue`, `CreateRegistryKey`, `DeleteRegistryKey`; `RegFileChanges.From` переводит разобранный файл в изменения в порядке файла.
- План: один load/unload на куст, порядок внутри куста сохраняется; шаги несут признак CurrentControlSet. Удаление корня куста блокируется. Отпечаток плана (формат 2) включает байты значений.
- Исполнитель: CurrentControlSet разрешается один раз на куст из `Select\Current`; без него шаг падает, ControlSet001 не подставляется. До первой записи проверяется, что все файлы кустов плана есть в образе: в `install.wim` нет `UsrClass.dat` профиля Default, поэтому изменения `HKCU\Software\Classes` в этот куст не пишутся (найдено в VM).
- `HKCU\Software\Classes` — через первый вход (решение владельца): изменения собираются в .reg (v5, UTF-16, `RegFileWriter`), файл кладётся в `ProgramData\ImageForge\FirstLogon` образа (`MountFileWriter`, без перехода по ссылкам и junction), а в SOFTWARE регистрируется компонент Active Setup с `StubPath` `reg.exe import`. Имя файла и GUID компонента — от хеша содержимого. Ни в какой другой куст эти изменения не пишутся. Проверка: шаг 2б [S2-REG-APPLY](vm-checks/S2-REG-APPLY.md) и [S2-FIRST-LOGON](vm-checks/S2-FIRST-LOGON.md).
- Найдено в VM: удаление значения открывало ключ только на чтение («Отказано в доступе»), исправлено.
- Engine: запись сырых байтов любого типа 0..b, удаление значения, создание ключа, удаление дерева в глубину без перехода по символьным ссылкам (дерево со ссылкой не удаляется).
- Превью: общий русский текст для окна и утилиты (`RegistryPreviewText`).
- Утилита: `reg-apply` и `reg-verify` — применить файл к смонтированному образу и проверить итог. Проверка в VM — [S2-REG-APPLY](vm-checks/S2-REG-APPLY.md).
- Дальше: прежние данные в превью, импорт файла из окна (экран «Реестр»), запуск с изменениями из файла.

### Экран «Реестр» (импорт .reg из окна)

- Окно читает выбранный файл (до 512 КБ) и передаёт байты, выбранную кодировку и кодовую страницу движку (`PlanAsync(PlanOptions)`, протокол 3). Разбор и проверка — только в движке: `RegFileImport` → план.
- Ошибки файла возвращаются отдельно от ошибок плана, с номерами строк и русским текстом (`RegFileDiagnosticText`); файл с ошибкой не оставляет плана, прежний план сбрасывается. В статусе показывается, как файл был декодирован.
- Без файла по-прежнему планируется маркер M1.
- Проверка в VM — [S2-REG-UI](vm-checks/S2-REG-UI.md).

### Appx: список и удаление по полному имени

- Core (TDD), `ImageForge.Core.Appx`:
  - `PackageIdentity.Parse` — строгий разбор полного имени `Имя_Версия_Архитектура_Ресурс_Издатель`: имя из букв, цифр, `.` и `-`, версия из четырёх частей, архитектура `neutral|x86|x64|arm|arm64`, `~` как пустой ресурс, издатель из 13 символов base32. Семейство — `Имя_Издатель`. Всё остальное отклоняется, поэтому в аргументы DISM не попадает ничего лишнего.
  - `DismAppxListParser` — вывод `/English /Get-ProvisionedAppxPackages`: блоки `Ключ : Значение`. Блок без PackageName, с неверным именем или с полями, не совпадающими с именем, и вывод без строки об успехе — проблема; со списком с проблемами удаление не планируется.
  - `AppxWarnings` — предупреждения для Microsoft Store и App Installer.
- `DismCliArguments.GetProvisionedAppx` и `RemoveProvisionedAppx` (имя проверяется повторно).
- Утилита: `appx-list` и `appx-remove` (удаляет, только если пакет есть в свежем списке, затем сверяет список ещё раз). Проверка в VM — [S2-APPX-INVENTORY](vm-checks/S2-APPX-INVENTORY.md).
- Дальше: список приложений в окне (нужен смонтированный образ), удаление в плане и в запуске с проверкой свежести списка, порядок по зависимостям.

### Appx: удаление из окна и в запуске

- Чтение списка (`ImageInspection`): исходник копируется и проверяется в `base\` (эту копию переиспользует следующий запуск), копия монтируется только для чтения в `inspect\`, список читается, монтирование всегда сбрасывается. Оставшаяся папка `inspect\` переводит рабочую папку в восстановление; восстановление сбрасывает это монтирование.
- План: изменение `RemoveProvisionedAppx(семейство)` разрешается в точные PackageName по последнему списку сессии. Без списка, с проблемным списком или для семейства, которого нет в образе, план блокируется. Библиотеки блокировались по именам; с чтением манифестов это заменено (см. ниже). Отпечаток плана (формат 3) включает удаления и отпечаток списка.
- Запуск: шаг `appx` после монтирования и до реестра. Список образа сравнивается по отпечатку со списком превью; при расхождении запуск останавливается до первого удаления. После удалений список читается снова, каждый удалённый пакет должен исчезнуть.
- Протокол 4: `InspectAsync`, `PlanOptions.RemoveAppx`, `PlanSummary.AppxRemovals`; возможность «appx».
- Окно: раздел «Приложения» — чтение списка, флажки, пометки для Store, App Installer и библиотек; удаления в превью. Рабочая папка открывается заново только при смене папок, чтобы не терять прочитанный список.
- Проверка в VM — [S2-APPX-UI](vm-checks/S2-APPX-UI.md).
- Дальше: зависимости из манифестов пакетов и порядок удаления по ним (вместо блокировки библиотек), дружественные имена.

### Appx: зависимости из манифестов

- `PublisherId` — id издателя из строки Publisher (SHA-256 UTF-16LE, первые 64 бита, base32 Крокфорда); сверено с `8wekyb3d8bbwe` и `cw5n1h2txyewy`.
- `AppxManifestParser` — AppxManifest.xml (идентичность, `Framework`, `PackageDependency`, `MainPackageDependency`) и AppxBundleManifest.xml (пакеты приложения). DTD запрещены, лимит 1 МБ, всё неверное — «не прочитано».
- `AppxManifestStore` — при чтении списка с монтирования: бандл читается через пакет приложения для x64 (затем neutral, x86), обычный пакет — напрямую. Манифест принимается, только если его имя, издатель и версия совпадают с пакетом. Пути строятся только из имён, ссылки и reparse points не проходятся (`MountFileReader`). Зависимости встроенных приложений (`Windows\SystemApps`) собираются отдельно.
- План: пакет с непрочитанными зависимостями не удаляется; пакет, который нужен оставшемуся приложению или встроенному приложению, не удаляется, в сообщении названы зависимые; удаления упорядочены так, что зависимое идёт раньше; круг блокирует. Библиотека блокируется, пока чьи-то зависимости не прочитаны. Список библиотек по именам удалён.
- Окно: «библиотека» в деталях, «Нужна приложениям: …».
- Утилита: `appx-list` печатает зависимости и число непрочитанных.
- Проверка в VM — [S2-APPX-DEPS](vm-checks/S2-APPX-DEPS.md).

### Features и Capabilities: список, подробности, изменение по одному

- Core (TDD), `ImageForge.Core.Features`:
  - `DismFeatureListParser` — вывод `/English /Get-Features`: блоки `Feature Name` и `State`. Имя компонента — буквы, цифры, `.`, `-`, `_`. Состояния `Enabled`, `Disabled`, `Disabled with Payload Removed`, `Enable/Disable Pending`; любое другое сохраняется как есть и помечается неизвестным (такой компонент план менять не будет). Неверное имя, блок без состояния, повтор и вывод без строки об успехе — проблема.
  - `CapabilityIdentity` — строгий разбор имени `Имя~Архитектура~Ресурс~Язык~Версия` (пустые части допустимы, `VBSCRIPT~~~~`). `DismCapabilityListParser` — `/Get-Capabilities`, состояния `Installed`, `Not Present`, `Install/Uninstall Pending`, остальные неизвестны.
  - `DismInfoParser` — поля `/Get-FeatureInfo` и `/Get-CapabilityInfo` для показа.
- `DismCliArguments`: включение компонента без `/All` (родители не добавляются незаметно) и всегда с `/LimitAccess` (без Windows Update); выключение без `/Remove`; удаление Capability. Имена проверяются повторно.
- Утилита: `feature-list`, `feature-info`, `feature-enable`, `feature-disable`, `capability-list`, `capability-info`, `capability-remove` (изменение — только для того, что есть в свежем списке, затем список читается снова). Проверка в VM — [S2-FEATURES-INVENTORY](vm-checks/S2-FEATURES-INVENTORY.md).
- Дальше: родители компонента и автоматически добавляемые действия, источники (sources\sxs для NetFx3, локальная папка FoD для добавления Capability), список в окне, изменения в плане и запуске.
- Найдено в VM: Dism.exe пишет перенаправленный вывод в OEM-кодировке (866 на русской системе), а читался он как UTF-8, и русские названия превращались в `?`. Теперь вывод читается в OEM-кодировке системы; ASCII, по которому работают разборщики, в ней тот же.

### Features: родители и источник NetFx3

- Engine: родители каждого компонента — через DISM API (`DismGetFeatureParent`, одна офлайн-сессия на смонтированный образ; у Dism.exe такой команды нет). ManagedDism открывает эту функцию только по имени или пути пакета, а компонентам базового пакета нужен `DismPackageNone`, поэтому вызывается его закрытая перегрузка.
- Core (TDD), `FeatureDependencies`: включение добавляет всех выключенных родителей (родители раньше), выключение — все включённые зависимые компоненты (зависимые раньше). Добавленное показывается отдельно, компоненты без payload помечаются как требующие источника. Неизвестные родители, компонент не из образа, неизвестное или незавершённое состояние в цепочке и цикл блокируют изменение целиком.
- `DismCliArguments.EnableFeatures` / `DisableFeatures` — несколько `/FeatureName:` в порядке изменения, без `/All`; включение всегда с `/LimitAccess`, `/Source:` только локальный абсолютный путь.
- `FeatureSources.NetFx3Problem` — папка-источник NetFx3 должна содержать пакет `microsoft-windows-netfx3-ondemand-package~...~amd64~...cab` (`sources\sxs` дистрибутива).
- Утилита: `feature-parents`, `feature-enable <имя> <папка|none>`, `feature-disable` с зависимостями. Проверка в VM — [S2-FEATURES-DEPS](vm-checks/S2-FEATURES-DEPS.md).
- Найдено в VM: офлайн-включение часто оставляет компонент в `Enable Pending` (завершается при первой загрузке) — это состояние считается включённым, `Disable Pending` — выключенным. DISM при включении сам добавляет вложенные компоненты по умолчанию (у `IIS-WebServerRole` — ещё 9), и заранее их не сообщает ни один API. Поэтому после изменения сравнивается весь список компонентов (`FeatureDependencies.Compare`), а превью в окне должно предупреждать, что DISM может добавить вложенные компоненты, и показывать их после запуска.

### Features и Capabilities: в окне, в плане и в запуске

- «Прочитать образ» читает приложения, компоненты Windows с родителями и подписями и дополнительные компоненты (Capabilities) с подписями за одно монтирование только для чтения. Если родители хоть одного компонента не прочитаны, менять компоненты нельзя.
- Core (TDD), `PipelinePlanner`: изменения `EnableWindowsFeature`, `DisableWindowsFeature`, `RemoveCapability` планируются только по прочитанному списку. Включение и выключение собираются через `FeatureDependencies`, добавленное показывается отдельно. Конфликт (выключается родитель того, что включается) и компонент без payload, кроме NetFx3 при наличии пакета в `sources\sxs`, блокируют план. Capability удаляется только установленная, по полному имени. Отпечаток плана (формат 4) включает отпечатки обоих списков.
- Запуск: шаги `capabilities` и `features` после `appx` и до реестра. Перед изменением список образа сверяется с отпечатком из превью; после — читается снова, каждое изменение и всё, что DISM изменил сам, пишется в журнал; включённое должно быть `Enabled`/`Enable Pending`, выключенное — `Disabled`/`Disable Pending`.
- Окно: разделы «Компоненты Windows» (отметка — состояние после запуска) и «Дополнительные компоненты» (отметка — удалить). Превью показывает добавленное планом, источник NetFx3 и предупреждение о вложенных компонентах, которые может включить DISM. Протокол движка 5.
- Проверка в VM — [S2-FEATURES-UI](vm-checks/S2-FEATURES-UI.md).
- Дальше: добавление Capability из локальной папки FoD, затем драйверы.

### Capabilities: добавление из папки FoD

- Core (TDD): `FeatureSources.FodProblem` — источник Features on Demand должен быть папкой `LanguagesAndOptionalFeatures` ISO: пакеты `.cab` и `metadata\DesktopTargetCompDB_FOD_Neutral.xml.cab`. Совпадение сборки ISO и образа проверяет только DISM. `DismCliArguments.AddCapability` — только локальный абсолютный путь и всегда `/LimitAccess`.
- Утилита: `capability-add <mount> <имя> <папка FoD>` — добавляет только компонент со статусом `Not Present`, затем читает список снова и печатает всё, что DISM изменил сам. Проверка в VM — [S2-FOD-ADD](vm-checks/S2-FOD-ADD.md).
- Дальше: выбор папки FoD и добавление в окне, в плане и в запуске.
