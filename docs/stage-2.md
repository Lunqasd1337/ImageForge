# Этап 2 — основные операции

Порядок по плану: `.reg`, Appx, Features/Capabilities, драйверы, обновления Windows; каждая возможность с тестами и проверкой в VM.

## Журнал работ

### Импорт .reg: загрузчик и парсер

- Core (TDD), `ImageForge.Core.Registry.RegFile`:
  - `RegFileLoader` — байты в текст. BOM решает UTF-16LE или UTF-8. Без BOM чистый ASCII читается сразу; текст с нулевыми байтами или корректный UTF-8 с не-ASCII блокируется как неоднозначный, пока пользователь не выберет кодировку; иначе — ANSI с показанной кодовой страницей. Некорректные байты, UTF-16BE и неизвестная кодовая страница блокируют импорт.
  - `RegFileParser` — REGEDIT4 и Version 5.00: `[key]`, `[-key]`, именованные и `@` значения, `=-`, строки с экранированием `\\` и `\"`, `dword:`, `hex:` и `hex(0..b):` с продолжением строк, комментарии `;` (внутри строки `;` — данные). Порядок операций сохраняется, включая повторы и удаления. Каждая ошибка — с номером строки, любая ошибка блокирует весь файл. Типы вне 0..b блокируются.
  - `RegData` хранит тип и байты ровно в том виде, в каком их записывает `RegSetValueEx`: строки — UTF-16LE с завершающим нулём, `REG_EXPAND_SZ` без раскрытия переменных. В REGEDIT4 строковые типы в hex — ANSI-байты, они переводятся в UTF-16LE по кодовой странице.
- Утилита: `reg-check <file.reg> <encoding> <code-page> <key>` — разбор файла и побайтное сравнение каждого значения с живым реестром (только чтение). Проверка в VM — [S2-REG-PARSE](vm-checks/S2-REG-PARSE.md).
- Дальше: маппинг всех корней из таблицы плана, применение к офлайн-кустам, превью с прежними данными, экран «Реестр».
